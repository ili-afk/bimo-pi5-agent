# 21. WorkBuddy API через сторонний клиент (n8n, Pi) — можно ли и что вместо

**Дата:** 08.10.2026
**Вопрос:** «можно ли использовать данный токен через n8n или как-то иначе, т.к. в РФ есть проблемы с этим (сейчас VPN только у приложения WorkBuddy AI)». Плюс: бан уже был получен один раз за использование больше 3 токенов за раз.

---

## 0. TL;DR

| Вопрос | Ответ |
|---|---|
| Технически можно вызвать API из n8n? | **Да.** Это `POST https://www.workbuddy.ai/v2/chat/completions` + `Bearer <JWT>` + `X-User-Id`. n8n сделает это узлом HTTP Request |
| Стоит ли это делать? | **Нет.** Это тот же маршрут «не из клиента», за который у вас уже заблокированы аккаунты |
| Помогут ли правильные заголовки? | **Нет.** Проверено 17.09.2026 — подстановка полного набора клиентских заголовков ничего не изменила |
| Почему? | Детект идёт по **отсутствию телеметрии устройства**, а не по токену |
| Ваш бан за «>3 токенов» | Это `10105` → `quota_active_session`. У вас сейчас `round_robin` по 6 аккаунтам и `max_live_sessions: 2` |
| Что делать вместо | n8n → **ваши собственные шлюзы**: `nvidia-proxy:8787` (nemotron-3-ultra-550B) и `vibe-proxy:8317` |

**Коротко:** n8n технически подключится, но это будет **худшая** версия того, что вы уже делаете из Hermes — без телеметрии, обычно с серверного IP, и с тем же результатом. Аккаунт `807a0901…` из ваших текущих шести — уже в списке заблокированных на этом маршруте.

## 2. Технически: да, n8n подключится

Форма запроса (для узла **HTTP Request** в n8n):

| Поле | Значение |
|---|---|
| Method | `POST` |
| URL | `https://www.workbuddy.ai/v2/chat/completions` |
| Header | `Authorization: Bearer <JWT>` |
| Header | `X-User-Id: 8658268e-24f3-4a94-aed8-8b8d87e921c8` |
| Header | `Content-Type: application/json` |
| Body | `stream: true` — **обязательно**, иначе `11101` |

Правила формата (18 правил `ModelCompatibilityProcessor` в клиенте — сторонний клиент не применяет ни одного, поэтому их надо повторять руками):

| Модель | Что реально должно уходить |
|---|---|
| `kimi-k3` | `thinking:{type:"enabled"\|"disabled"}`; **без** `reasoning_effort` и `temperature`; в каждом `assistant` — `reasoning_content` |
| `kimi-k2.5` / `kimi-k2.6` | `thinking:{type:…}`; мышление вкл → `temperature: 1`, выкл → `temperature` нет; `reasoning_content` (заглушка `"-"`) |
| `gpt-5.5` / `gpt-5.4` / `gpt-5.3-codex` | `reasoning_effort` работает; `max_tokens` → `max_completion_tokens` |
| `gemini-2.5` / `gemini-3` | `reasoning_effort` удаляется; `thought_signature` в первом `tool_call` |

Плюс всегда: не отправлять `verbosity` и `reasoning_summary`. `GET /v2/models` не существует (404) — список моделей только из конфига.

## 3. Практически: нет — и вот доказательства

Это не мнение, а результат ваших же прошлых замеров, зафиксированных в скилле `workbuddy-model-catalog`.

### 3.1 Детект идёт по телеметрии, а не по токену

> «Детект "запрос не из клиента" идёт по **отсутствию телеметрии устройства** (Tencent Galileo OTLP `otlp.j.woa.com`, `machineId` = `wmic csproduct UUID`, `qimei36`), а не по токену.»

То есть сервер смотрит не на то, **чем** вы авторизовались, а на то, **пришла ли вместе с запросом телеметрия устройства**. У n8n её нет и быть не может — n8n это серверный процесс.

### 3.2 Заголовки не помогают — проверено

> «Подстановка полного набора клиентских заголовков проверена 17.09 — результат не изменился.»

### 3.3 Доказательство из кода клиента

В бандле есть `ENV_KEY_CODEBUDDY_SKIP_INTERNAL_HEADERS` — **штатный режим самого клиента**, в котором он отправляет запрос вообще без внутренних заголовков (`X-Skip-Auth-Interceptor: 1`). Если официальный клиент умеет ходить без заголовков, значит набор заголовков **не является условием допуска**, и «дособрать заголовки» — заведомо не тот путь.

### 3.4 Аккаунты, уже заблокированные на этом маршруте

`iliamih01`, `iliamih09`, `goodguyyyyy`, **`807a0901…`**

Последний — **один из шести ваших текущих аккаунтов**.

### 3.5 Коды, при которых надо остановиться

| Код | HTTP | Что значит | Действие |
|---|---|---|---|
| **11128** | 400 | `Illegal API invocation from an unapproved channel` | **остановиться**, не ретраить |
| **11140** | 403 | `request illegal` — бан/запрет аккаунта | **остановиться**, не ретраить |

**Ловушка:** `11140` сервер маскирует под `displayMsg.en` = «The content did not pass the safety review. Please adjust and retry.» Причина **не** в тексте промпта — в аккаунте. Не искать «запрещённые слова».

## 4. Ваш бан: что именно произошло

«Больше 3 токенов за раз» — это код **`10105` → `quota_active_session`** (категория `quota`). Сервер считает **одновременные живые сессии**.

Что этому способствует в вашей конфигурации:

| Настройка | Значение | Влияние |
|---|---|---|
| `credential_pool_strategies: custom:workbuddy-api` | `round_robin` | запросы расходятся по шести аккаунтам — со стороны сервера это выглядит как параллельные сессии |
| `max_live_sessions` | `2` | уже опущено ниже трёх — это правильная реакция |
| Число аккаунтов | 6 | чем больше пул, тем легче превысить лимит одновременных |

**Вывод:** `round_robin` по шести аккаунтам — прямая причина. Если маршрут вообще использовать, то только с одним аккаунтом и `max_live_sessions: 1`.

## 5. Проблема РФ/VPN — для n8n она острее, чем для Hermes

| Клиент | Выход | Телеметрия устройства | Итог |
|---|---|---|---|
| Приложение WorkBuddy AI | свой встроенный туннель | **есть** (Galileo OTLP, machineId, qimei36) | работает |
| Hermes на вашем ПК | VPN/прокси на ПК | нет | уже привёл к банам |
| **n8n** | обычно серверный/VPS IP | **нет** | **хуже обоих** |

n8n — это серверный процесс. Он:
1. **не имеет доступа к встроенному туннелю приложения** — туннель живёт внутри Electron-клиента;
2. **не имеет телеметрии устройства**;
3. обычно стоит на VPS, то есть с IP датацентра — а это само по себе признак «не клиент» и одновременно гео-блокировка.

Получается двойной красный флаг: датацентровый IP **и** отсутствие телеметрии.

## 6. Что делать вместо этого

n8n нужен как оркестратор — отлично. Но направлять его надо не в WorkBuddy, а **в ваши собственные шлюзы**. Они дают **более крупные модели**, работают из РФ и не несут риска бана.

| Куда направить n8n | Base URL | Модели |
|---|---|---|
| `nvidia-proxy` | `http://<пк>:8787/v1` | **nemotron-3-ultra-550B-a55b**, nemotron-3.5-lightning-30b-a3b, moonshotai/kimi-k3 |
| `vibe-proxy` | `http://<пк>:8317/v1` | NVIDIA (120B/550B), Claude Sonnet 4.5, Gemini, OpenRouter через релей |

Актуальное состояние на 03.10.2026 (из вашего конфига): у `nvidia-proxy` **четыре модели из шести отключены** (`410 Gone` — `nemotron-3-super-120b-a12b`, `deepseek-v4-flash-0731`, `minimax-m3`, `gpt-oss-120b`). Живые: `nemotron-3-ultra-550b-a55b`, `nemotron-3.5-lightning-30b-a3b`, `nemotron-3-nano-omni-30b-a3b-reasoning`, `moonshotai/kimi-k3`.

Плюс у вас есть отдельный быстрый профиль `nvidia-proxy-fast` — по вашему же замеру медиана **889 мс** против 2075 мс у lightning и 7114 мс у kimi-k3.

**Ключевая мысль:** 550B-модель у вас уже доступна законным путём через API-ключ. Она крупнее всего, что есть в линейке WorkBuddy. Дополнительный риск бана за неё платить не нужно.

### Если n8n нужен именно наружу

Тогда выход — не WorkBuddy, а ваши же механизмы:
- **Cloudflare-воркер** `nvidia-api-proxy.iliamih09.workers.dev` — по вашему замеру отдаёт **200 и с VPN, и без**;
- **релей** `egress/worker.js` из `vibe-proxy` — универсальный посредник с белым списком.

## 7. Отдельно: безопасность

В `config.yaml` секреты лежат **открытым текстом**: JWT WorkBuddy, ключ `freemodel.dev`, ключ `aerolink`, токен Telegram-бота. Файл стоит держать вне синхронизаций и репозиториев, а ключи — переносить в переменные окружения (у вас уже есть механизм `key_env`, которым пользуются `nvidia-proxy` и `binjack-litellm`).
