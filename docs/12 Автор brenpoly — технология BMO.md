## Конечный автомат (ядро архитектуры)

```
WARMUP → IDLE ⇄ LISTENING → THINKING → SPEAKING → IDLE
                              ↓
                    CAPTURING (камера) / ERROR
```

- **WARMUP** — прогрев: `ollama.generate(keep_alive=-1)` держит модель в памяти.
  Без этого LLM «загружалась» на каждый запрос, как «заводить машину на каждом повороте».
- **IDLE** — слушает кодовое слово (или кнопку).
- **LISTENING** — запись + транскрипция (Whisper).
- **THINKING** — агентский цикл (см. ниже).
- **SPEAKING** — потоковый TTS + проигрывание.
- **CAPTURING** — снимок с камеры, затем возврат в цикл с картинкой.

Каждое состояние = **смена лица + случайный звуковой клип** из папки.
Случайность сделана специально, чтобы не звучать как «заготовленные ответы».

> ⚠️ В видео 3 автор **убрал** озвучку состояния LISTENING: она перебивала
> самого пользователя. Вместо неё сделал движение сервоприводом. Это ровно та
> проблема, которую решает наш пункт про barge-in.

## Агентский цикл: как работает «инструмент»

Самый ценный для нас фрагмент. Реализовано **без MCP** — на «one-shot prompting»:

1. В системный промпт вшиты **примеры**:
   ```
   User: What time is it?     → {"action":"get_time","value":"now"}
   User: Search for news…     → {"action":"search_web","value":"robots news"}
   User: What do you see?     → {"action":"capture_image","value":"environment"}
   ```
2. LLM решает: если нужен инструмент — выводит **JSON**, иначе — обычный текст.
3. `execute_action_and_get_result()` проверяет действие по белому списку
   `VALID_TOOLS = {get_time, search_web, capture_image}`.
4. Есть таблица **алиасов** для галлюцинаций модели:
   `google/browser/news → search_web`, `look/see → capture_image`.
5. Результат возвращается в LLM как `RESULT: … \nUser Question: …`, и цикл повторяется,
   пока модель не выдаст финальный текст.

**Вывод:** это упрощённый MCP своими руками. Наш план (MCP → Hermes) — тот же
принцип, только стандартизованный и с внешними инструментами.

Практическая деталь автора: **маленькие модели плохо «угадывают» JSON**, поэтому
алиасы и примеры в промпте обязательны.

## Как сделана «своя» озвучка (видео 2) — knowledge distillation

Задача: BMO говорит голосом актрисы корейского происхождения. Zero-shot клонеры
слишком тяжёлые для Pi. Решение — **дистилляция в маленькую модель**:

1. **CozyVoice** (Apache-лицензия, обучен на данных добровольцев) — генерация
   ~500 клипов с нужным акцентом из публичного источника.
2. Источник — **LibriVox** (public domain), транскрипт — через Whisper.
3. **Fine-tune модели Piper** на этих клипах (через обёртку «Text-to-Speechy»).
4. Результат — `bmo.onnx`, просто подменяет файл голоса.

> Для нас это **этап «потом»**: сначала edge-tts ru-RU, своя озвучка — когда
> всё остальное работает.

## Бенчмарки ускорителей (видео 2) — важный отрицательный результат

| Сетап | TTFT (текст) | TTFT (зрение) | TPS |
|---|---|---|---|
| **CPU Raspberry Pi 5** | базовая | базовая | базовый |
| **Raspberry Pi AI HAT+ 2** (Hailo-10H, 40 TOPS INT4, 8 ГБ) | лучше всех | в 2 раза лучше CPU | **чуть хуже CPU** |
| **M5Stack LLM-8850** (24 TOPS INT8, 8 ГБ) | средний | **<1 с — лучший** | **лучший** |

**Что из этого следует:**
- Ускорители **ограничивают выбор моделей** — работают только предустановленные
  (пришлось перейти с Gemma на Qwen 2.5 1.5B).
- Hailo даёт свой Ollama-обёртку, поэтому код почти не менялся.
- 8850 — «чёрный ящик», метрики приходилось оценивать по логам.
- **Автор остался на голом CPU** — ради гибкости менять модели одной строкой.

> 🔑 Прямой аргумент в пользу облачного подхода: любое локальное железо
> **фиксирует** набор моделей. Облако позволяет менять модель в конфиге.

## Видео 3: движение и запуск игр

- **Серво** на руку BMO: подшипник + 3D-кронштейн, поворот ~180°.
  Питание взято **напрямую с 5 В**, к Pi идёт только управляющий провод —
  потому что Pi 5 капризен к питанию.
- **Новый инструмент**: запуск Steam через **Moonlight** (клиент на Pi)
  + **Sunshine** (хост на ПК) — стриминг игр по домашней сети.
  Это ровно модель «устройство отдаёт команду ПК».
- **Odradek** (Death Stranding): отдельная сборка — роботизированная рука
  со сканером. К BMO отношения не имеет, это «вторая половина видео».

## Чему учит этот проект (выводы для «Джарвиса»)

**Совпадает с нашим планом (хороший знак):**
1. Конвейер wake word → STT → LLM → TTS — тот же.
2. **OpenWakeWord** — модель лежит в репозитории (`wakeword.onnx`), обучается на Colab.
   ⚠️ README утверждает «Hey Jarvis», но фактически модель обучена на **«Hey BMO»** —
   это подтверждено открытым issue #26 (открыт 13.09.2026, не исправлен). То есть
   «Hey Jarvis» из README — ошибка документации, а не готовое решение. Модель
   всё равно надо обучать свою.
3. Инструменты как функции + JSON-вызов = MCP своими руками.
4. Пробуждение кнопкой как альтернатива кодовому слову.
5. Прогрев моделей и борьба за задержку — то же, что наше Г-4.

**Отличается (и это осознанный выбор):**
| | BMO (автор) | «Джарвис» (мы) |
|---|---|---|
| Мозг | локально, Ollama | облако, свой Worker |
| Железо | Raspberry Pi 5, 16 ГБ, ~15 000 ₽ | ESP32-S3, ~3 000 ₽ |
| Язык | английский | русский |
| Модель | 1–2B параметров | 100B+ через API |
| Стоимость | 0 ₽/мес, но железо дорогое | 0 ₽/мес, железо дешёвое |
| Автономность | полная (офлайн) | нужен интернет |
| Гибкость моделей | низкая (что влезло) | высокая (base_url) |

**Главный урок автора, который стоит запомнить** — он сам его произносит в финале:
у локальных моделей **трудно ставить guardrails** и они **запирают в узкий набор моделей**.
Плюс: чтобы получить качество, сравнимое с облаком, нужен Pi 5 за 15 000 ₽ —
то есть в 5 раз дороже нашего железа, и всё равно слабее по уму.

**Вывод:** наш выбор «облако + дешёвый ESP32-спутник» для бюджета 2 000–5 000 ₽
и русского языка — **обоснован**. Мы не «упрощаем», мы меняем дорогое железо
на бесплатный API. Но архитектуру (конвейер, состояния, инструменты, barge-in)
берём у автора практически как есть.

## Что стоит скопировать буквально

1. **Конечный автомат** IDLE/LISTENING/THINKING/SPEAKING/ERROR/WARMUP — у нас те же состояния.
2. **WARMUP** — прогрев LLM при старте (у нас: первый «пустой» запрос к Worker).
3. **Алиасы инструментов** — защита от галлюцинаций малых моделей.
4. **Случайные звуковые клипы** вместо фиксированных — ощущение живости.
5. **Отдельный микроконтроллер под кнопки** — у нас кнопки читает сам ESP32, это проще.
6. **Проверка кода перед запуском** — автор отдельно предупреждает об этом в описании
   (и это же касается любых скачанных прошивок).

## Что не копировать

1. Локальные модели на слабом железе — мы уходим в облако.
2. `memory.json` — у нас SQLite.
3. tkinter-GUI — у нас OLED + светодиодное кольцо.
4. Тяжёлую 3D-обвязку (серво, рука Odradek) — не наша задача.
